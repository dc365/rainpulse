## 1. 本轮交付与边界

新后台沿用首版的 React → Go → PostgreSQL / NATS / Python Worker。
没有增加 Kubernetes、Redis、新的工作流引擎或进程管理平台。

- **数据台账**：独立按站点、时间和处理阶段查询注册体扫；没有预报产品的资料也能看到。站点概况、来源详情、阶段资产完成标记检查、候选重算和下游引用关联；可直接带入重算预检查。
- **性能分析**：按真实执行尝试和完整执行身份分组；区分入队、原生执行、发布和结果登记，显示分位数、有效样本数量与慢任务入口。
- **执行资源**：按 qc/render/diagnostics 管理池持久化接单策略；暂停接单、等待当前任务排空、恢复接单，保留操作原因和策略版本。
- **任务日志**：服务端按级别、尝试ID、关键字筛选，然后稳定分页；默认最新窗口、可查看历史或跟随，导出的是当前窗口而不是全部历史。
- **入队时间**：新任务、上游解锁和真实重试分别记录；执行尝试冻结自己的入队时间。消息重新投递不重置等待时长，旧记录不回填假时间。

未改变天气算法、近站阈值、QC标志、QI、缺测语义、业务资格或自动链路主题。
候选不会因为“计算成功”覆盖当前QC、拼图、QPE或预报；没有增加默认展示切换。
本轮没有完整的源文件扫描器、全资产清理、实时自动Worker硬件监控、全链路预报重算或个人账户系统。

## 2. 使用路径

### 查资料 → 看来源 → 预检查 → 原任务中心

进入“数据台账”，选择最多24小时的 UTC+8 时间范围，可按站号和阶段过滤。
返回的是登记台账，不是每次打开页面就扫描对象存储。
站点概况包含数据库已知但此范围未到报的站点；不根据六分钟产品步长推算原始体扫应有数量。

点击“来源／检查／重算”，查看当前最新扫描工作流的 normalized/QC/grid 指针、
相关自动任务、候选管理任务、下游分析引用。每组关联最多最新100条；截断明确提示。
下游体扫关联不等于使用了最近的QC候选，不能以此作为完整的删除影响分析。

“检查完成标记”由服务端从当前登记指针读取 `_SUCCESS.json`，记录检查时间、URI、
声明的包大小、声明的包摘要和实际标记摘要。检查期间指针改变会拒绝登记。
`marker_checked` **仅代表完成标记结构与声明摘要约束经过检查**；不代表重新下载了
所有对象，也不证明整包内容完整、扫描身份独立可信或气象质量合格。
连接失败、权限失败与非法标记统一保守标记为 `unverified`，不能冒充“资产一定缺失”。
旧URI检查不会被用作新URI的检查结果。用户没有任意传入对象URI或删除对象的入口。

台账的重算入口携带站点和体扫所在的一分钟区间，不直接提交计算。必须核对计划实际
包含的体扫；同一分钟有多个登记时可能生成多个任务。已有冻结计划不会覆盖这次带入的选择。
仍支持首版三个预设：单站QC+对照图、已有QC仅重建图件、已有区域诊断任务重建。

### 资源接单控制

“暂停接单并排空”写入 `ops_pool_controls`；Claim 在事务内取得同一池行的共享锁，
策略修改取得独占锁。因此修改返回后，不会再有绕过新策略的后续领取。
在修改之前已经领取的任务允许继续；心跳、日志、完成与恢复登记不受此策略限制。

新注册Worker遵守数据库池策略，不能用自身 ready/busy 心跳重置策略。
Worker只有取得显式 `accepting:true` 的新鲜注册回执才拉取消息；数据库Claim仍是最终裁决。
缺少/过期回执时停止拉取，不把“池暂停”视为不健康反复重启。
同一Worker已有RUNNING/COMMITTING尝试时，事务拒绝再次领取，避免心跳滞后造成重复占槽。

界面同时显示运行数、租约过期数、活动作业排队数、已知最老入队时间及配置就绪Worker数。
“配置就绪”不等于“当前空闲”；排队任务的冻结身份仍须有匹配Worker。
失联尝试继续占据活动计数，不能从“心跳过期”推导“进程已退出”。

策略变更使用 `expected_revision`；多个浏览器同时修改时，旧版本收到409并刷新确认，
不会静默强制覆盖。操作原因保存在独立资源操作记录，主体仍为共享 administrator，
并非已经完成逐人身份审计。没有容器强杀、任意终端或自动改变CPU/内存配额。

## 3. 性能统计口径

查询最多7天、最多10000次管理尝试，按 started_at 半开区间筛选；超过10000拒绝并要求
缩小范围或选择执行身份，不静默采样。数据库查询同样有有界结果数。

每种 kind + 完整 fingerprint 独立统计。失败、受阻、取消、撤销和未完成按状态计数；
**耗时分位数只包含成功尝试**，不代表全部尝试的延迟分布。P50/P95为所有实测样本的
nearest-rank，不对各Worker的P95求平均。零是合法测量；缺失、负数、NaN不充当零。
每项单独给出样本数，少于20条提醒样本较少。

| 指标 | 来源与解释 |
|---|---|
| `queue_ms` | 此次尝试的数据库 queued_at → started_at；包括等待策略恢复的时间，不声称是纯调度器开销 |
| `attempt_elapsed_ms` | 数据库领取 → 结果登记；可能包含登记恢复等待，不是纯计算耗时 |
| `compute_wall_ms` | 原生执行总耗时，包括准备、计算、编码等，不与其子阶段相加 |
| `input_read_ms/context_ms/qc_core_ms/serialize_validate_ms` | 原算法已提供时才统计，缺少就保持未知 |
| `publication_wall_ms` | 管理Worker产物发布耗时；原生执行之后的阶段 |
| `process_rss_sampled_peak_bytes` | 单次尝试执行窗口内进程采样峰值，不是该任务独占内存；采样可能错过短尖峰 |
| `input_bytes/output_bytes` | 已上报的字节数，不冒充网络吞吐或主机资源占用 |

新重试只重置新任务等待段，旧尝试的时间永远保留；Wake/消息重投不重置入队时间。
旧数据 `queued_at=NULL`，列表显示“未采集”，不从 created_at/dispatched_at 反推。
原自动链路旧的发布即RUNNING口径本轮未改；它的统计与新管理执行池分开。
同一执行身份仍可能有不同输入规模、上下文、缓存冷热、节点和配额，不自动宣布版本更快。

## 4. 日志分页

任务／作业 `/events` 支持 `direction=backward&before=...` 与原有 forward/after。
`level/attempt/q` 在服务端SQL的 LIMIT 前生效；关键字是字面量子串，`%` 和 `_` 不是通配符。
必须限定一个run或task，避免全库任意搜索；关键字最多128字符，接口每页最大500。
返回显示顺序始终按事件ID升序；历史页面游标指向当前窗口最旧ID。

界面默认取最新200条，历史前后翻页和跟随互斥。跟随刷新最新200条，而不是保证浏览器
永不遗漏的无限流；高流量时可暂停跟随并向前翻页。导出明确标注“当前窗口”。
已有2000条／尝试存储上限保持不变；不是提供无限日志保留。
事件时间继续为服务端接收时间，不把排序后的日志当精确算法时间线。

系统日志仍为首版可选Loki接口，本轮没有自动安装、配置或宣称接通journald采集。

## 5. 升级顺序（重要）

源码包不连接数据库、不修改部署，不自动执行这些步骤。

### 5.1 先完成旧身份任务

Worker执行身份包含Python源码，本轮变更 `operations/worker.py` 会改变身份。
**不能直接拿新镜像接管旧冻结计划**。使用旧运行版本先停止新增管理提交，
等待既有管理作业／尝试完成或按旧版受控取消／恢复流程处理；失败和暂停作业也必须
有明确处置，不能因为队列看起来空就忽略未发出的旧任务意图。
不要为了恢复而清空身份校验、修改旧计划摘要或覆盖已保存候选。

从v1首次升级时不存在v2池策略，不能用新页面宣称旧服务已经暂停。使用已有维护流程
控制入口与旧Worker生命周期。自动链路是否暂停由现场维护范围决定，不在本补丁强制切换。

### 5.2 测试库先验证SQL

先确认已有管理v1表；全新安装先执行首版 `schema.sql`。升级v1则仅执行增量：

```bash
# PG连接参数由本机受保护配置提供；不要把凭据写入版本库。
psql -X -v ON_ERROR_STOP=1 -f services/control/internal/operations/schema_v2.sql
```

脚本包含自身事务，增加两列、三张小管理表及相关索引，不回写历史任务时间。
普通CREATE INDEX在维护窗口执行，会涉及锁与空间；应先评估当前ops表大小。
IF NOT EXISTS允许正常重复执行，但不等于验证同名列／索引定义完全一致；已有人工修改
数据库结构时先核对。这里不修改已存在的自动链路业务表，也不删除历史记录。

### 5.3 协调更新

完成测试后构建新Go、Web及管理Worker镜像。沿用现有 `configure_admin_ops.py` 的实际
镜像／配置／挂载／CPU内存预算，不覆盖当前近站profile或基础部署清单。
先启动可识别schema2的新Go API，再启动新管理Worker；新Worker面对旧API缺少
accepting回执会停止拉取，不在不明确策略下继续执行。

`GET /api/v1/admin/ops/status` 新增 `management_schema:2`；公开管理响应schema仍为1.0，
OpenAPI版本为1.1.0。只有迁移后数据库就绪，页面才显示可用。
池默认ACCEPTING用于首次初始化；重复迁移不会把已有DRAINING重置。

检查全部管理Worker新鲜注册与配置身份后，重新创建/预检查新版本计划。
不要把旧冻结计划静默重绑定到新镜像。本轮不自动切换业务产品。

宣称系统仍遵守暂停**。先停止新增管理提交、协调任务和Worker，再按旧版维护流程回退。
