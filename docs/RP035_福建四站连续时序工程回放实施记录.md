## NowcastInput 门禁结论

RP-013 `rp013-fixed-5min-v1.1` 要求：

- 3 至 6 个连续五分钟时次；
- 所有时次业务合格；
- 每帧有效覆盖率至少 0.70；
- 每帧平均 QI 至少 0.45。

本序列满足时次连续和网格身份一致，但三个分析都不是业务合格输入；覆盖率为
0.3827 至 0.4170，平均 QI 为 0.2391 至 0.3997，也低于冻结质量门槛。

对 10:00 UTC 执行只读式创建预检时，控制面返回：

```text
RadarAnalysis 1922303f-eef9-583b-acb6-11644f3f1cc6 is not operationally eligible
```

预检前后相应 forecast run 数都为 0，因此没有遗留失败预报，也没有用降低门槛的方式
伪造真实福建短临。

## QPE 完成事件边界修复

09:55 QPE 产物首次写入后，Worker 报告完成，但控制面保持 `QPE_RUNNING`。根因是控制面
比较双精度未截断峰值和 float32 产品峰值时使用固定 `1e-6 mm/h` 容差：

```text
uncapped double = 86.46816701021315
float32 product = 86.46817016601562
difference      = 0.00000315580247
```

这是正常的 float32 量化差，不是 QPE 超过物理上限。修复改为使用该数值转换为 float32
后的下一可表示值作为上界，仍会拒绝真实的明显越界。新增测试执行了红绿验证：旧逻辑下
真实样本失败，修复后通过；`86.47 mm/h` 的明显越界仍被拒绝。

同时，JetStream 结果消费者现在会记录被拒绝事件的 subject 和具体错误，避免无效结果
被终止后只留下数据库 RUNNING 状态而没有控制面日志。仓库范围检查确认，未发现第二处
相同的未截断 QPE 峰值比较。

105 的 orchestrator 镜像是从 `.build/linux-amd64/rainpulse-orchestrator` 复制的 scratch
镜像。仅执行 `docker compose build` 不会编译源码。本轮已按正确顺序在本地交叉编译
Linux 二进制、同步到 105、再重建并核验容器二进制。修复部署后，使用不可变
`_SUCCESS.json` 中原完成事件重新投递一次，09:55 状态成功收敛为 `ANALYSIS_READY`。
原始数据、产物和数据库行均未删除。
